## From PMO pass, 2026-08-19 — #324.4 CSP worker

- [x] **MEDIUM — CSP blocked a `blob:` worker (#324.4)**: DONE 2026-08-19, **but not the way the issue proposed**. Traced the worker to `canvas-confetti`: its default export is `confettiCannon(null, { useWorker: true, resize: true })`, so the first call builds a worker from `URL.createObjectURL(new Blob([...]))`. Production CSP declared no `worker-src`, so it fell back to `script-src`, which has no `blob:` — blocked, and the library logged "🎊 Could not load worker" on every page that fires confetti. **Nothing was ever visually broken**: canvas-confetti catches the failure and renders on the main thread.
  - The QA report proposed `worker-src 'self' blob:`. **Rejected**: a `blob:` worker source lets any XSS execute attacker-supplied code in a worker, and the only thing it buys is moving a decorative animation off the main thread. Widening a security policy for confetti is a bad trade.
  - Instead: `workerSrc: ["'self'"]` set explicitly in `server/index.ts` so the policy is a decision rather than an accidental fallback, and a `client/src/lib/confetti.ts` wrapper (`create(undefined, { useWorker: false, resize: true })` — the default instance minus the worker) that all three components now import.
  - Guard: `server/tests/csp_worker_src.test.ts` fails if `blob:` ever appears in `workerSrc`, or if any client file imports `canvas-confetti` directly and reinstates `useWorker: true`. Proven to fail on both regressions before being trusted.
  - **Verified**: firing confetti in a browser constructs **zero** workers and logs no fallback warning. Not verified visually — the preview renderer stays backgrounded, so `requestAnimationFrame` is paused and the canvas never paints in that environment. The drawing path is untouched by this change; only the thread it runs on differed.
